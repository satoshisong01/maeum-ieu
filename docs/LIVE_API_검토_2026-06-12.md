# Gemini Live API 도입 검토 — 음성 첫 응답 6초 벽 깨기

> 2026-06-12. T2 음성 UX의 구조적 한계(STT→LLM→TTS 직렬, 실측 첫 응답 6.1~6.5s) 해소 검토.
> ~~결론: TEXT 응답 모달리티로 단계 도입 권장~~ → **PoC 실측으로 수정(아래 §0)**: 가용 Live 모델은 TEXT 모달리티 미지원 — AUDIO + 출력 전사 게이트 전략으로 변경. **첫 음성 1.44초(76% 단축) 실측.**

## 0. PoC 실측 결과 (2026-06-12, scripts/poc-live-api.mjs)

| 측정 | 결과 |
|---|---|
| 가용 모델 | `gemini-2.5-flash-native-audio-preview-12-2025` (+3.1-flash-live-preview). **둘 다 TEXT 모달리티 거부(1007)** — AUDIO 전용 |
| 발화 종료 → 첫 오디오 | **평균 1,437ms** (thinkingBudget 0 적용. 미적용 시 4,076ms — thinking이 +2.6s) |
| 발화 종료 → 첫 출력 전사 | **평균 972ms** — 오디오보다 ~0.5s 선행 → **재생 전 안전망 게이트 가능** |
| 입력 전사 | 발화 중 실시간 도착(종료 전 -1.1s) — 인지분석 입력으로 즉시 가용 |
| 현행 대비 | 6,100~6,500ms → 1,437ms = **약 76% 단축** |

핵심 발견·트레이드오프:
1. **TEXT 모달리티 불가** → 3-1의 "기존 TTS 유지" 전략 폐기. 대신 **출력 전사 선행 도착**을 이용해 클라가 오디오 청크를 ~0.5s 버퍼링하며 전사를 후처리(누출·회상정답 검사) → 통과 시 재생하는 게이트 구조 가능 (체감 첫 음성 ~2초).
2. **thinkingBudget 0이 Live 경로에선 정상 작동** (3/3 응답 수신) — 현행 채팅 경로의 "0 금지(빈응답)" 규칙과 다름. 모델·프로토콜이 달라서이며, 도입 시 회귀 관찰 필요.
3. **입력 전사 품질 리스크**: "무릎이 좀 시큰거려서"→"무료 피 좀 시큼거려서" 오인식 관측 — 인지분석 입력으로 쓰기엔 현행 STT(2.5-flash)보다 거칢. 도입 시 인지분석용 전사는 별도 검증 필요(녹음본 병행 전사 또는 전사 신뢰도 게이트).
4. **보이스 변경**: 음성이 Cloud TTS Neural2(현행 지윤 목소리)가 아닌 Gemini 보이스로 바뀜 — 사용자 체감 변화, 보이스 선택(30종) 검토 필요.
5. ephemeral token 발급 엔드포인트 작동 확인 (`POST /api/live/token` — 미로그인 401, 로그인 200, 모델 제약·1회용·30분 만료).

## 1. 현재 구조 vs Live API

```
[현재]  녹음 종료 → 업로드 → STT(3.2~3.7s) → LLM 첫문장(2.6s) → 문장단위 후처리 → TTS(0.3s) → 재생
        = 첫 음성까지 6.1~6.5s (실측, scripts/measure-voice-latency.mjs)

[Live]  말하는 동안 오디오 스트리밍 → (발화 종료 감지=VAD) → 모델이 즉시 응답 생성
        = STT 왕복이 사라짐. 입력 전사(input_audio_transcription)는 부산물로 제공
```

## 2. 기술 사실 (공식 문서 기준)

| 항목 | 내용 |
|---|---|
| 프로토콜 | WebSocket 양방향. SDK(@google/genai — **이미 마이그레이션 완료**) 지원 |
| 모델 | `gemini-2.5-flash-native-audio-preview`(thinkingBudget), `gemini-3.1-flash-live-preview`(thinkingLevel) |
| 응답 모달리티 | AUDIO(네이티브 음성) 또는 **TEXT** 선택 가능 |
| 전사 | 입력·출력 모두 transcription 제공 (인지 분석 입력으로 사용 가능) |
| 툴 사용 | 지원. 2.5는 비동기 함수콜(NON_BLOCKING) — 응급/검진 게이트를 서버 툴로 호출 가능 |
| 세션 한도 | 음성 전용 15분 (세션 관리 기법으로 연장 가능), 컨텍스트 128k |
| VAD | 자동(감도·침묵시간 설정 가능) — 현재 클라 VAD 대체 |
| 인증 | 클라→Gemini 직결 시 **ephemeral token** 필수 (서버가 토큰만 발급) |

## 3. 아키텍처 결정 2가지

### 3-1. 연결 토폴로지: 클라 직결 + Vercel은 토큰 발급만 (권장)
- Vercel 서버리스는 상시 WebSocket 서버 불가 → 중계 서버를 두려면 별도 인프라(Cloud Run 등) 필요.
- 공식 패턴인 **클라이언트 직결 + ephemeral token**이면 Vercel에 토큰 발급 엔드포인트(POST 1개)만 추가하면 됨. 인프라 증설 0.
- 트레이드오프: 서버가 대화 스트림 중간에 끼지 못함 → 저장·분석은 전사 이벤트를 클라가 서버로 회송(기존 /api/chat 저장 경로 재사용).

### 3-2. 응답 모달리티: TEXT (핵심 결정 — 안전망 보존)
- **AUDIO(네이티브)**: 음성이 모델→클라로 직행. 운율·자연스러움 최상. **그러나 후처리 파이프라인(회상 정답 차단·환각 전제 삭제·호칭 정정·누출 차단)이 전부 사후화** — 이미 재생된 뒤 전사로만 확인 가능. 어르신 안전 도메인에서 수용 불가 수준의 리스크.
- **TEXT**: 모델은 텍스트 스트림으로 응답 → **기존 문장단위 postProcessReply + Cloud TTS 경로 그대로** 사용. 잃는 것은 네이티브 운율뿐, 안전망·기존 코드 자산 전부 보존.
- 지연 예산(TEXT 모달리티): VAD 종료 ~0.3s + 첫 문장 생성 ~2.0-2.6s + TTS 0.3s ≈ **2.6~3.2s** (현재 6.1s에서 ~50% 단축).

## 4. 비용 비교 (공시 단가, 2.5 기준)

| 항목 | 현재 (standard) | Live API |
|---|---|---|
| 오디오 입력 | $1.00/M tok (STT 호출) | $3.00/M tok (3배, 단 발화 분량만 — 시간당 발화 30분 기준 ≈ $0.14) |
| 텍스트 입력(프롬프트) | 턴마다 ~11k 재전송 ($0.30/M) | **세션 내 컨텍스트 유지 — 재전송 없음** (신규 토큰만 과금) |
| 텍스트 출력 | $2.50/M | $2.00/M (2.5 native-audio의 TEXT 출력) |
| 음성 출력 | Cloud TTS 별도(현행 유지) | TEXT 모달리티면 동일하게 Cloud TTS |

→ 오디오 입력 단가 3배는 토큰량이 작아 영향 미미. **세션 컨텍스트 유지로 11k 프롬프트 재전송이 사라지는 게 오히려 절감 요인** (explicit caching과 같은 효과를 세션이 공짜로 제공). 총비용은 대략 중립~소폭 절감으로 추정, 도입 시 DEBUG_USAGE 상당 로깅으로 실측 필수.

## 6. 단계 계획 (착수 시)

1. **PoC (1일)**: ephemeral token 엔드포인트 + 클라 직결 + TEXT 모달리티 + 기존 TTS — 지연 실측만
2. **게이트 통합 (1~2일)**: 입력 전사 서버 회송 → 응급/검진/모더레이션 게이트 클라 인터럽트 설계
3. **저장·분석 연결 (0.5일)**: 전사 → Message 저장 + 인지 분석 호출 (기존 경로 재사용)

5. 안정화 후 native AUDIO 모달리티 재평가 (운율 가치 vs 안전망 사후화 — 제품 결정)
