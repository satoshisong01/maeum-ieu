# 마음이음 검증 가이드 (Verification Guide)

> **작성 이유.** 2026-10-02, 사용자 지적: *"뭐 찾을 때마다 문제가 나온다 = 이전 작업에서 미처 보지 못한 코드가 많다는 뜻이다."*
> 맞는 지적이고, 원인은 게으름이 아니라 **구조**였다. 기존 플레이북(`검증_플레이북.md`)은
> *무엇을 돌릴지*는 정의했지만 *빠뜨렸는지 증명하는 장치*가 없었다. 게이트가 전부 행위·E2E라
> **한 번도 실행되지 않은 분기**가 보이지 않았고, 그래서 "전부 통과"가 "전부 검증됨"을 뜻하지 않았다.
>
> 이 문서는 그 구멍을 메우는 **기준**이다. 플레이북이 *체크리스트*라면 이 문서는 *합격 조건*이다.
> 둘은 대체 관계가 아니라 상하 관계다 — 플레이북의 항목을 돌리되, 합격 여부는 여기 기준으로 판정한다.

---

## 0. 이 프로젝트에서 "검증했다"가 뜻하는 것

**근거 없이 '확인했다'고 말하지 않는다.** 다음 셋 중 하나를 제시할 수 없으면 그 항목은 미검증이다.

| 증거 등급 | 형태 | 예 |
|---|---|---|
| **A. 실행 증거** | 명령과 그 출력 | `342/342 passed`, `Branches: 57.22%` |
| **B. 코드 증거** | 파일:라인 + 인용 | `prompt.ts:200 — pro 분기가 scoringTurn을 설정하지 않음` |
| **C. 부재 증거** | 없음을 보인 검색 | `grep -rn "probeTurn" app/ lib/` 결과 전량 열거 |

금지 표현: "문제없어 보입니다", "정상 동작할 것입니다", "아마 괜찮습니다".
불확실하면 **불확실하다고 적는다.** 추정을 사실처럼 보고한 적이 있고(2026-10-01 SG 포트 제거,
Gmail 비밀번호 11자 주장), 둘 다 사용자가 되물어서야 바로잡혔다. 그 비용이 신뢰다.

## 1. 이 저장소가 실제로 당해 온 결함 유형 (사냥 목록)

새 코드를 검증할 때 **이 목록을 하나씩 대조한다.** 범용 체크리스트보다 이게 훨씬 잘 잡는다.
각 항목은 실제 사고에서 유도했다.

| # | 유형 | 증상 | 탐지법 |
|---|---|---|---|
| F1 | **조용한 모델 강등** | 인자 누락·플래그 미설정으로 저가 모델이 쓰임. 에러 0, 품질만 하락 | 모델 선택 인자를 호출부 전수 grep. 기본값이 있는 파라미터를 특히 의심 |
| F2 | **死 정규식** | `\b`가 한글에 무력, greedy가 조사 흡수, alternation 순서로 분기 사망 | `regex-battery.ts`에 케이스 추가. 활용형·조사·사투리 변형 전수 |
| F3 | **파일 간 파서 드리프트** | 같은 포맷을 두 곳에서 파싱하다 한쪽만 수정 | 포맷 문자열을 grep해 파싱 지점이 몇 개인지 먼저 센다 |
| F4 | **fail-open → always-open** | 장애 시 통과시키는 설계가 평시에도 통과시킴 | 성공 경로와 실패 경로를 **둘 다** 테스트. 성공 시 차단되는지 반드시 확인 |
| F5 | **양쪽 다 통과하는 테스트** | 수정 전 코드로도 녹색 | 수정을 되돌려 **실제로 실패하는지 확인**하고 그 사실을 보고에 적는다 |
| F6 | **보장을 참칭하는 주석** | 주석이 코드보다 많은 걸 약속 | 주석의 주장을 코드로 재확인. 틀렸으면 주석이 코드보다 위험하다 |
| F7 | **측정 자체가 거짓** | 숫자가 실제를 반영하지 않아 그 위 판단이 전부 무효 | 측정 도구의 범위를 먼저 검증 (예: 342건이 커버리지에 잡히는가) |
| F8 | **위음성 우대 실패** | 안전 판정이 애매할 때 "아님"으로 기움 | 응급·인지이상은 애매하면 **양성** 쪽으로. 반대는 사람이 다친다 |
| F9 | **역할 간 데이터 누수** | 모드/계정 분리가 한 경로에서만 적용 | 4역할 × 진입점 행렬로 전수. chat만 고치고 live·observe를 빠뜨린 전례 |
| F10 | **고아 코드** | 리팩토링 후 끊긴 import·호출 — 경로가 죽은 흔적일 수 있다 | eslint no-unused-vars 경고를 "사소"로 넘기지 말고 **왜 끊겼는지** 추적 |

## 2. 커버리지 — "안 지난 분기"를 기계적으로 드러낸다

### 왜 이게 핵심인가
2026-10-01 응급 복원력 수정 당시, 기존 게이트 4종이 **새 분기를 하나도 실행하지 않았다.**
수정 전 코드로도 전부 통과했을 테스트였다. 사람의 성실성으로는 이걸 못 막는다. 도구가 막아야 한다.

### 측정 범위
`vitest.config.ts`의 `SAFETY_CRITICAL` 9개 파일에만 임계치를 건다.
전역 평균은 **금지** — 테스트하기 쉬운 유틸이 어려운 안전 경로의 공백을 가린다.

```
npx vitest run --coverage
```

### 래칫 규칙
- 임계치는 **올리기만 한다.** 현재 바닥(2026-10-02 실측): lines 73 / functions 72 / branches 57 / statements 69.
- 안전 핵심 파일을 수정하면, 그 파일의 분기 커버리지가 **수정 전보다 낮아지면 안 된다.**
- 내려야 한다면 아래 '임계치 변경 절차'를 따른다.

### 임계치 변경 절차 (내리는 경우)
1. 어떤 테스트가 왜 사라졌는지 적는다.
2. 그 분기가 **도달 불가**임을 코드로 증명하거나, 대체 게이트(safety-regression 등)를 제시한다.
3. `vitest.config.ts`에 근거 주석을 남긴다. 숫자만 바꾸는 커밋은 거부한다.

### 측정 경과와 현재 상태 (2026-10-02)

도입 당시 41.29% → **80.53%**. 중간의 57.22%는 '숫자를 정직하게 만든' 단계다
(safety-regression 342건이 커버리지에 안 잡히고 있었다 — F7).

| 파일 | 분기 (도입시 → 현재) | 상태 |
|---|---|---|
| `lib/chat/emergency-llm.ts` | 0% → **100%** (18/18) | ✅ LLM 백스톱, 변이 3종 검증 |
| `lib/chat/emergency-notify.ts` | 26.1% → **79.1%** (91/115) | ✅ SSRF 가드 포함, 변이 4종 검증 |
| `lib/chat/emergency.ts` | 23%(거짓) → 78.4% (58/74) | ✅ safety-regression 342건이 커버 |
| `lib/chat/korean-particle.ts` | 37%(거짓) → 65.2% (30/46) | ⚠ **다음 목표** — F2(死 정규식) 상습 지점 |
| 나머지 5개 | 85~100% | ✅ |

남은 최대 구멍: `korean-particle.ts` 16개 분기. 이 파일은 후처리 정규식이라
F2(死 정규식) 사고가 반복된 지점이므로 우선순위가 높다.

## 3. 비용과 품질을 함께 판정한다 (사용자 1순위 기준)

> *"최적의 비용으로 최고의 효율. 비용 맞춘다고 기능이 떨어지면 안 된다."*

비용 변경은 **단독으로 평가하지 않는다.** 아래 두 축을 한 표에 같이 적어야 판정이 성립한다.

| 축 | 측정 | 합격 조건 |
|---|---|---|
| **원가** | `scripts/usage-stats.ts`, `DEBUG_USAGE=1` 윈도우 집계 | 턴당 원가 하락 또는 동결 |
| **품질** | 해당 경로의 결정적 게이트 (judgment/matrix/eval) | **하락 0** — 1건이라도 떨어지면 불합격 |

### 모델 변경 시 필수 절차
1. 변경 전 기준선을 **수치로** 기록 (케이스 통과수 + 턴당 원가).
2. 변경 후 같은 케이스셋 재실행. `scripts/compare-models.ts` 활용.
3. 품질이 동률 이하면 **비용이 아무리 싸도 불합격**. 되돌린다.
4. 확인 턴(probe)·검진(pro)·응급 판정은 **비용 최적화 대상에서 제외**한다 —
   여기서 아낀 돈보다 놓친 치매·응급의 비용이 크다. (2026-09-30 실측: 동반자 모델을
   내리자 확인턴 지시 준수가 깨져 선별이 조용히 멈췄다.)

### 안전 기능은 과금·제한의 대상이 아니다
응급 감지·보호자 알림은 결제 상태·일일 제한과 무관하게 동작해야 한다.
일일 제한 게이트가 음성 응급을 삼킬 뻔한 전례가 있다(STT 완료 전 판정).

## 5. 누락 방지 프로토콜 (Anti-skip)

검증을 "돌렸다"고 보고하기 전에 **반드시** 아래를 수행한다.

### 5.1 선언 → 실행 → 대조
1. 시작 전, 이번 검증이 다룰 항목을 **목록으로 선언**한다 (TodoWrite 또는 보고 서두).
2. 각 항목마다 §0의 증거 A/B/C 중 하나를 남긴다.
3. 끝난 뒤 선언 목록과 증거를 **1:1 대조**한다. 증거 없는 항목은 "미실행"으로 보고한다.

### 5.2 금지된 축약
- ❌ "나머지도 비슷하므로 생략" — 비슷하지 않았던 전례가 F3(파서 드리프트)다.
- ❌ "시간상 일부만" — 시간은 제약이 아니다(사용자 명시: *"일주일이 걸리든 한 달이 걸리든"*).
- ❌ 서브에이전트 보고를 검증 없이 수용 — 오탐 전례 있음(2026-10-01 "L3에 after() 폴백 없음"은 거짓).
  주장은 **직접 코드를 읽어** 확인한 뒤에만 채택한다.

### 5.3 완결성 비평 (마지막 단계)
검증을 마쳤다고 생각한 시점에, 다음 질문에 답을 적는다.
- 돌리지 **않은** 양식이 있는가? (정적/단위/E2E/라이브/비용/보안 중)
- 증명하지 **않은** 주장이 있는가?
- 읽지 **않은** 파일이 변경 범위에 있는가?
- 이번 변경이 §4 행렬의 다른 칸에 닿는가?

하나라도 "있다"면 검증은 끝나지 않았다. 그 항목으로 돌아간다.

## 6. 실행 순서 (전체 검증 1회)

| 단계 | 명령 | 소요 | 합격 |
|---|---|---|---|
| 1. 타입 | `npx tsc --noEmit` | ~30s | 에러 0 |
| 2. 린트 | `npx eslint .` | ~30s | 에러 0 (경고는 §1 F10으로 추적) |
| 3. 단위+게이트+커버리지 | `npx vitest run --coverage` | ~1m | 전수 통과 + 임계치 충족 |
| 4. 프롬프트 누출 | `npm run audit:prompt-leak:ci` | ~10s | 0건 |
| 5. 사용자 스코프 | `npm run audit:user-scope` | ~30s | 0건 |
| 6. 빌드 | `npx next build` | ~3m | 성공 |
| 7. 라이브 E2E | `node scripts/e2e-roles.mjs 30 <role> headless` × 3역할 | ~30m | 플래그 0 |
| 8. 수동 안전 스팟 | 플레이북 §B 목록 | ~20m | 전항 통과 |
| 9. 비용 | `npx tsx scripts/usage-stats.ts` | ~1m | §3 기준 |
| 10. 완결성 비평 | §5.3 | ~5m | 네 질문 전부 "없다" |

1~6은 **매 커밋**, 7~10은 **기능 변경·릴리스 전**.

## 7. 결함 발견 시 (루프)

1. **재현** — 실패하는 테스트를 먼저 쓴다. 재현 못 하면 결함이 아니라 가설이다.
2. **원인** — 증상이 아니라 원인을 고친다. 같은 원인의 다른 발현처를 §4 행렬로 찾는다.
3. **수정**
4. **되돌림 검증** — 수정을 임시로 되돌려 테스트가 **실제로 실패하는지** 확인 (F5).
5. **회귀 고정** — vitest 또는 safety-regression에 케이스 추가. 정규식 수정은 regex-battery 필수.
6. **커버리지 확인** — 해당 파일 분기 커버리지가 내려가지 않았는지.
7. **기록** — `docs/CYCLE_FIXLOG.md`에 발견·수정·**미해결**을 구분해 솔직하게.
8. **보고** — 발견 문제 우선, 수치와 함께. 못 한 것을 먼저 말한다.
